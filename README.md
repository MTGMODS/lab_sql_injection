# Лабораторна робота №10 — SQL-ін’єкції

Навчальний PHP-ресурс «Щасливий квиток»: реєстрація, вхід, новини `news.php?id=` і таблиця користувачів із логінами та паролями у відкритому вигляді.

Дві копії сайту:

| Порт | Каталог | Що це |
|------|---------|--------|
| 8080 | `vulnerable/` | Слабка система: SQL склеюється з введенням користувача, помилки БД видно на сторінці, паролі без хешу |
| 8081 | `secure/` | Той самий функціонал, але PDO prepared statements |

Це стенд для власної лабораторної. Не викладайте вразливу версію у відкритий інтернет без обмеження доступу.

## Запуск на сервері (Ubuntu)

```bash
sudo apt update
sudo apt install -y php-cli php-sqlite3
chmod +x start.sh
./start.sh
```

Сайт слухає `0.0.0.0:8080` і `0.0.0.0:8081`. Відкрийте ці порти в фаєрволі лише для себе (IP гуртожитку / VPN), не для всього світу.

Або через Docker:

```bash
docker compose up --build
```

## Що показувати на відео (мапа методички)

1. ОС і наявність PHP на сервері / ВМ.
2. Сайт з реєстрацією, логінами й паролями в БД (файл `vulnerable/data/app.db`).
3. Перевірка свого ресурсу за шаблоном з додатку: у вас є рівно такий URL, як у списку дорків — `news.php?id=`.
4–5. Демонстрація атаки — **ваша** частина звіту на **цьому** стенді. Готових пейлоадів і команд сканерів у репозиторії немає.
6–8. Порівняти код `vulnerable/login.php` і `vulnerable/news.php` з `secure/…`, повторити ту саму спробу на порті 8081, показати сторінку `recommendations.php`.
9. Скрінкоду «було / стало» + робота форм.

Пункт 5 про брутфорс хешів **не застосовується**: паролі навмисно збережені відкритим текстом. Після отримання рядків з таблиці `users` вхід виконується цими паролями напряму.

## Де саме вразливість у коді

`vulnerable/login.php` — логін і пароль вставляються в лапки SQL-рядка.

`vulnerable/news.php` — параметр `id` вставляється в запит як частина SQL.

`vulnerable/register.php` — те саме для `INSERT`.

`secure/` — запит константний, дані передаються в `execute()`.

## Відповіді на питання до лабораторної

**1. Що таке SQL-ін’єкція?**  
Це атака, коли введення користувача потрапляє в текст SQL-запиту і змінює його логіку. Її використовують, щоб обійти авторизацію або прочитати чужі рядки БД. Вона працює тоді, коли додаток склеює SQL рядком і не відокремлює код запиту від даних.

**2. Які вразливості потрібні?**  
Немає параметризації, часто ще й видно помилки СУБД. Приклад — `vulnerable/login.php` і `vulnerable/news.php`.

**3. Методика.**  
Знаходять параметр, який потрапляє в SQL (`id`, логін). Змінюють значення так, щоб СУБД виконала не той запит, який задумав розробник. На відео показуєте це на порту 8080, потім ту саму спробу на 8081.

**4. Вимоги до захищеної розробки.**  
Див. сторінку `/recommendations.php` на захищеній версії: prepared statements, без виводу SQL-помилок, валідація типів, хеш паролів у реальному проєкті, мінімальні права БД, екранування HTML.
