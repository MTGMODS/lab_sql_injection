Мета роботи

Ознайомитися з підсистемою захисту ОС Windows 11: керування обліковими записами та
групами, дискреційне розмежування доступу (ACL), аудит і перегляд журналу безпеки.


Обладнання та ПЗ

- Віртуальна машина з Windows 11 Pro.
- Обліковий запис адміністратора.
- Вбудовані засоби: Local Users and Groups, Local Security Policy, властивості NTFS,
  Event Viewer.


Політика безпеки (неформальна)

Об’єкт політики: навчальна КС у ВМ (каталог `C:\Project`).

Групи:
- Developers — розробка коду: повний доступ до `Source`, читання `Docs` і `Logs`.
- Testers — тестування: зміна вмісту `Tests`, читання `Source` і `Docs`.

Користувачі:
- dev1, dev2 — члени Developers.
- tester1 — член Testers.

Вимоги до паролів:
- мінімальна довжина 8 символів;
- увімкнені вимоги складності;
- історія паролів не менше 5;
- блокування облікового запису після 3 невдалих спроб входу на 30 хвилин.

Контроль доступу (файлові об’єкти):
1. `C:\Project\Source\created_by_dev.txt` — Developers: Full; Testers: Read.
2. `C:\Project\Tests\plan1.txt` — Testers: Modify; Developers: Read.
3. `C:\Project\Docs\Documentation.txt` — Developers і Testers: Read; аудит видалення.
4. `C:\Project\Shared\readme.txt` — Developers: Modify; Testers: Read.
5. `C:\Project\Private\admin_only.txt` — лише Administrators.
6. `C:\Project\Logs\access.log` — Developers/Testers: Read; Administrators: Full.

Реєстрація: аудит успішних і невдалих входів; для `Documentation.txt` — аудит видалення
та зміни дозволів.


Хід роботи

1. Вхід під адміністратором. Журнал «Безпека» очищено.
2. У `secpol.msc` налаштовано політику паролів, блокування та аудит входу / доступу до об’єктів
   згідно з політикою вище.
3. У `lusrmgr.msc` створено групи Developers, Testers і користувачів dev1, dev2, tester1.
4. Створено структуру `C:\Project` і шість файлових об’єктів. Для кожної папки/файлу
   налаштовано ACL (за потреби вимкнено успадкування), для Documentation.txt — SACL (аудит).
5. Виконано перевірки доступу під різними користувачами (див. протокол).
6. У Event Viewer переглянуто події входу та (за наявності) доступу до об’єктів.

Висновок

У ході роботи на практиці застосовано базові механізми захисту Windows 11: ідентифікацію
та автентифікацію користувачів, дискреційне розмежування доступу через ACL для файлових
об’єктів, політику паролів і блокування облікових записів, а також аудит із переглядом
журналу «Безпека». Перевірки показали, що система дозволяє санкціоновані дії членів груп
і блокує спроби вийти за межі призначених прав, а журнал фіксує події входу.


Відповіді на контрольні запитання

1) Які особливості має архітектура ОС Windows? Яке значення це має для властивостей системи?
Windows має гібридне ядро з розділенням режиму користувача та режиму ядра і шаром
апаратної абстракції (HAL). Збій програми в user mode зазвичай не валить ядро; прямий
доступ до обладнання з прикладних програм заборонений. Це підвищує стабільність і безпеку.

2) Які суб’єкти доступу існують в Windows?
Користувачі, групи, комп’ютери (у домені), а також вбудовані principals: SYSTEM, Everyone,
Authenticated Users, LOCAL SERVICE, NETWORK SERVICE тощо.

3) Яка архітектура системи ідентифікації і автентифікації Windows? У чому переваги?
Winlogon приймає інтерактивний вхід і делегує перевірку LSA; LSA використовує пакети
автентифікації (MSV/NTLM локально, Kerberos у домені тощо). Перевага — модульність:
можна підключати різні методи (пароль, смарткартка, біометрія) без зміни всієї підсистеми.

4) Де і в якому вигляді зберігаються образи паролів? Які вразливості?
Хеші паролів локальних облікових записів зберігаються у вулику SAM
(`C:\Windows\System32\config\SAM`). Використовується NT-хеш (історично також слабший LM-хеш,
у сучасних системах зазвичай вимкнений). Вразливості: офлайн-атака на копію SAM,
pass-the-hash, підбір слабких паролів.

5) Назвіть типові об’єкти доступу Windows. Доступ до яких об’єктів контролює система?
Файли, каталоги, ключі реєстру, процеси, потоки, служби, принтери, об’єкти ядра синхронізації,
токени тощо. Система розмежування доступу контролює всі захищувані об’єкти, що мають
дескриптор безпеки.

6) Які існують методи доступу? Які спільні для всіх видів об’єктів?
Є загальні/стандартні права (READ_CONTROL, WRITE_DAC, WRITE_OWNER, DELETE, SYNCHRONIZE)
та специфічні для типу об’єкта (для файлу — ReadData, WriteData, Execute тощо). Стандартні
права спільні для більшості захищуваних об’єктів.

7) Які стандартні групи користувачів існують у Windows? Які їхні повноваження?
Administrators — повний контроль над системою; Users — звичайна робота без зміни системи;
Guests — мінімальні права; Power Users (застаріла роль у нових Windows); Backup Operators —
резервне копіювання з обходом частини ACL; Remote Desktop Users — вхід через RDP тощо.

8) Яким чином Windows перевіряє можливість доступу?
При запиті доступу reference monitor порівнює SID користувача та груп із його access token
зі списком DACL об’єкта. Спочатку враховуються заборонні ACE, потім дозвільні. Якщо явного
дозволу немає — доступ за замовчуванням заборонено (SeAccessCheck).

9) У чому різниця в інтерпретації прав доступу для файлу і каталогу?
Для файлу права стосуються операцій над його вмістом (читання/запис даних). Для каталогу —
операцій зі списком і дочірніми об’єктами (створення файлів, перелік, траверс). Права часто
успадковуються від батьківського каталогу до дочірніх об’єктів.

10) Як відбувається в Windows тимчасове підвищення повноважень?
Через UAC: навіть адміністратор зазвичай працює з відфільтрованим токеном. Коли потрібні
підвищені права, система показує запит; після підтвердження процес отримує повний токен
адміністратора на час роботи.

11) Де зберігає система журнал реєстрації? Які можливості і недоліки захисту від НСД?
Журнали зберігаються у файлах `.evtx` у `C:\Windows\System32\winevt\Logs`. Доступ до них
обмежений ACL. Недолік: зловмисник з правами адміністратора може очистити або змінити
журнал; для протидії використовують централізований збір логів і захист/моніторинг цілісності.
